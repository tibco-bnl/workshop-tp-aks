## What is new

### Control Plane

- **Infrastructure resource customization:** CPU, memory, and storage for infrastructure components on Kubernetes and Control Tower Data Planes can be overridden in a YAML editor on the Data Plane configuration page. The official documentation topic is "Customizing Recipe Configuration for Kubernetes Data Planes".
- **On-demand infrastructure components (Control Tower):** a Control Tower Data Plane provisions only baseline infrastructure components automatically. Components such as the Hawk Console, BW Adapter, and MFT adapter are installed only when active capabilities require them, and can be installed later from the Data Plane configuration page.
- **Application Operator permission:** users can start, stop, restart, and scale applications and configure application environment variables, but cannot delete applications. The permission can be scoped to a namespace within a Data Plane.
- **Application log download:** history logs can be downloaded as plain text or CSV (matching the applied time range and filters), and real-time logs as text, directly from the Control Plane UI without access to the log server.
- **TESSA:** model calls can run on Amazon Bedrock in your own AWS account instead of a customer-provided OpenAI API key (you can switch between the two), and TESSA can interact with the EMS capability through the EMS MCP server.

### Capabilities

- **BusinessWorks 6 Containers:** new alert categories **Instance Count** and **App Status** (Running, Stopped, Scaling, Unknown); the Application Operator permission is supported (start, stop, manual scale, environment variables; no deploy, upgrade, delete, or auto-scale).
- **BusinessWorks 5 Containers:** the same two alert categories and Application Operator support; Zoom In, Zoom Out, and Reset controls on process diagrams; a new API under API Docs for actionable Hawk methods previously exposed through `/commands` on port 8090.
- **BusinessWorks 5 / Adapters on Control Tower:** RESTful APIs under `/cp/bw5/v1/ct` for applications, domains, machines, monitoring, installed software, plugins, and rulebases, and read-only tools in the BusinessWorks MCP Server for BW5 on-premise applications managed through Control Tower.
- **Flogo:** engine variables can use the **password** type (value masked in the UI); `build-tp-deployment` in the Flogo App Build CLI can include connector supplements in `build.zip`.

### Removed

- **NGINX Ingress Controller:** because community development of the NGINX Ingress Controller ended, its usage was removed from TIBCO Operated Control Plane. You may keep using it in your own deployments, but TIBCO no longer officially supports or recommends it with the Control Plane and Data Planes. This workshop uses Traefik for ingress; the NGINX option in the setup guide is retained only for existing environments.

## AKS requirements and operator notes

- The 1.22 system requirements are unchanged from 1.21 for Kubernetes and tooling: CNCF-certified Kubernetes with 1.35 certified, PostgreSQL 16 with `uuid-ossp` for self-hosted Control Plane, and Helm 3.17.0 or later. Check Azure regional/version availability and the current TIBCO requirements before choosing an AKS version.
- Keep the existing AKS storage and networking prerequisites. Use the Control Plane-generated Data Plane commands when registering a cluster because they include the selected per-Data-Plane connectivity and controller configuration.
- Do not plan new NGINX Ingress deployments; use Traefik or a supported Gateway API controller (see the official system requirements for the certified list).
- For air-gapped or private-registry deployments, use the matching 1.22.0 image manifests and the official image-sync scripts; push updated images before starting the upgrade.

## Upgrade from 1.21.0

The official upgrade assistant accepts a deployed Control Plane at `app_version` 1.21.0. Do not use it to skip a minor release.

1. Back up the database, Helm values, and required Kubernetes secrets. Record `helm history` and verify the Control Plane release is healthy.
2. If using a custom image registry, mirror the 1.22.0 images before upgrading. Run the official prerequisite validation script and `helm repo update`.
3. Use [`scripts/1.22.0/upgrade.sh`](https://github.com/TIBCOSoftware/tp-helm-charts/blob/main/scripts/1.22.0/upgrade.sh) and its README. The assistant checks the existing release is deployed at 1.21.0, generates versioned values or runs the Control Plane upgrade, and verifies the resulting release. Alternatively, follow the [official Helm upgrade commands](https://docs.tibco.com/pub/platform-cp/1.22.0/doc/html/Installation/upgrading-from-previous-version.htm).
4. **Values change handled by the assistant:** `tp-cp-o11y.capabilities.o11y.default` and `.withResources` were merged into `tp-cp-o11y.capabilities.o11y`. If your 1.21.0 values contain either section, the assistant sets `tp-cp-o11y.capabilities.o11y.overwriteRecipe` from the old `default.overwriteRecipe` (`"false"` if unset) and removes the old sections; other keys in those sections (chart versions, `isLatest`, release notes) are dropped so the 1.22.0 chart defaults apply. If you upgrade with manual Helm commands, make this change yourself.
5. Upgrade the decoupled capability charts after the Control Plane. Use the exact versions in the `control-plane`, `bw`, `flogo`, `developer-hub`, `hawk`, `messaging`, `mcp-hub`, and `be` artifact files.
6. Upgrade Data Plane infrastructure and capabilities from the Control Plane UI, including the observability capability (see PCP-25998 below). Verify the generated commands and the selected hybrid connectivity/controller options.
7. Confirm all Control Plane and Data Plane workloads are healthy and validate installed chart versions against the artifact manifests.
8. *(Optional)* Remove the stale `o11y-exporter.yaml` recipe. Data Planes that had Resources configured before the upgrade still have `/private/tsc/config/capabilities/platform/o11y-exporter.yaml` on the Control Plane PVC (`control-plane-pvc` by default). Nothing reads it, so leaving it has no functional impact. If you remove it, first confirm the consolidated recipe exists under `/private/tsc/config/capabilities/infra/`, and run the `kubectl exec` commands in a pod that mounts `tsc/config` (for example orchestrator, web-server, identity-management, or cronjobs), **not** the `o11y-service` pod. See the [official procedure](https://docs.tibco.com/pub/platform-cp/1.22.0/doc/html/Installation/upgrading-from-previous-version.htm).

The assistant requires Bash 4+, yq 4.45.4+, Helm 3.17+ and jq 1.8+ for Helm flows, and kubectl for post-upgrade checks. If `manageDbSchema` is false, follow the official external PostgreSQL schema-management procedure. Do not change the default registry or chart repository during this upgrade.

From 1.20.0 or earlier, upgrade one minor version at a time through [1.21.0](./v1.21.0) first.

## Known issues to review

- **PCP-26766:** after customizing the observability environment values in the recipe customization UI and then updating the observability resource configuration, the customized values reset to defaults in the UI and at runtime. No workaround.
- **PCP-25998:** after upgrading the Control Plane from 1.21 to 1.22, downloading real-time or history logs fails with "404 page not found" for applications on an existing Data Plane that has not been upgraded. Upgrade the Data Plane, including its observability capability, to 1.22. A newly registered Data Plane is not affected.
- **PCP-27651:** after upgrading Data Plane infrastructure components to 1.22.0, the Capability Provisioner and the application pod Fluent Bit sidecar (BW6 Containers) show error logs. The official list gives no workaround.
- **PCP-20136:** the documented cleanup workaround applies only when upgrading Control Tower Data Planes configured with NGINX Ingress. AKS Kubernetes deployments should review the official issue conditions before applying it.
- **PLTDX-1343:** on Azure with the `azure-files-sc` storage class, the Developer Hub PostgreSQL pod fails to start (`chmod ... Operation not permitted`). Use `azure-disk-sc` instead.

Review the full [official 1.22.0 known-issues list](https://docs.tibco.com/pub/platform-cp/1.22.0/doc/html/Release-Notes/known-issues.htm) before production changes.
